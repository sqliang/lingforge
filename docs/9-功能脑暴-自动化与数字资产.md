# 功能脑暴 · 第三轮：个人自动化与数字资产

> 版本：1.0（脑暴稿，待 review）
> 定位：第三轮脑暴。视角切换到「**AI 作为数字管家**」——个人自动化、文件与数据整理、财务记录。前序：[7-功能脑暴](./7-功能脑暴.md)（信息/知识/职业/生活事务）、[8-功能脑暴-创作与表达](./8-功能脑暴-创作与表达.md)（创作输出侧）。候选不重复，底座衔接 [6-综合平台升级评估方案](./6-综合平台升级评估方案.md)。
> 纪律不变：痛点优先、三维筛选、候选≠承诺、不确定性诚实标注。

## 0. 本轮视角说明

前两轮处理「信息」和「表达」。这一轮处理「**东西**」——每个人电脑和账户里都堆积着大量无人管理的数字资产与重复性数字劳动：

```text
数字管家痛点地图
─────────────────────────────────────────────────────────
M1 文件熵增：下载文件夹 3000 个文件，桌面是垃圾桶，
   「那个 PDF 我明明下载过」每周都在上演
M2 截图坟场：截图里有报错、灵感、账单、地址、二维码，
   截完即死，找的时候只能凭记忆翻时间
M3 记账坚持难：记账 App 下了五个，每个活不过两周——
   录入动作太反人性
M4 报销炼狱：发票散落邮箱/相册/微信卡包，
   月底贴报销单是酷刑
M5 财务状况黑盒：钱花在哪儿了、订阅合计多少、
   这个月比上月多花了什么——答不上来
M6 跨应用搬运工：每天重复「A 里看到 → 手动填进 B」，
   这就是没有 API 的人肉 iPaaS
─────────────────────────────────────────────────────────
横切痛点 Z：这些痛点的共性是「非结构化输入 → 结构化记录
   → 定期汇总」——恰好是「多模态感知（AI）+ 结构化存储
   （平台）+ 定时汇总（基建）」的三段式主场。
```

## 1. 候选功能池（10 个）

### 簇 K · 文件与截图（对应 M1/M2）

**K1. 文件整理 Agent**
- 痛点：下载/桌面文件夹熵增（M1）。
- 形态：指定受控目录 → Agent 扫描（文件名+类型+内容摘要）→ 提出整理方案（分类树+重命名规则+归档移动清单）→ **用户确认后执行**（审批门！）→ 整理报告。
- Agent 角色：内容理解与分类建议；**执行是确定性代码，且只在用户确认后**——延续「Agent 不直接持有权力」的平台哲学。
- 底座关系：这是**首个「本地文件系统」场景**，需要新的受控执行边界（白名单目录、只移动不删除、操作可回滚日志）——新基建，但哲学与 worktree 白名单一脉相承；整理报告=Artifact。
- 量级：M–L。不确定性：本地文件访问意味着部署形态变化（桌面端/本地守护进程），**与当前 Web 平台形态冲突**——这是最大的架构问题，可能需要「本地伴侣进程」设计，列为 L 的主因。

**K2. 截图管家** ⭐
- 痛点：截图即坟场（M2）。
- 形态：截图导入（拖拽/指定目录监控）→ OCR + 多模态理解（这是什么：报错/账单/灵感/地址/聊天）→ 自动打标 + 全文可搜 → 对话式找回：「上个月那张数据库报错的截图」。
- Agent 角色：多模态理解 + OCR + 语义检索。
- 底座关系：检索复用 docs/7 C1（embedding 管线）；图片=image Artifact；找回入口=ChatBot 知识库模式；打标结果入库。
- 量级：M（C1 之后）。不确定性：导入通道（Web 平台下「目录监控」同样受 K1 的部署形态限制——v1 妥协为手动拖拽/批量上传）。

**K3. 文档结构化（合同/保单/说明书）**
- 痛点：重要文件看不懂、关键条款找不到（docs/7 L3 的同族，本轮从「文件管理」角度补全）。
- 形态：上传 PDF/拍照 → 结构化提取（ parties/金额/期限/关键条款/注意点）→ 「这个合同里关于违约的部分怎么说」问答 → 到期条款自动登记到 docs/7 D1 到期哨兵。
- Agent 角色：文档解析 + 条款提取 + 问答（RAG）。
- 底座关系：文档=Artifact；问答=ChatBot 知识库模式；与 D1 的联动是杀手细节。
- 量级：M。不确定性：红线同 docs/7——只做「解释+提示注意点」，不做法律/保险建议。

### 簇 L · 财务记录（对应 M3/M4/M5）

**L1. 对话记账 Agent** ⭐
- 痛点：记账死于录入摩擦（M3）。
- 形态：输入框直接说「午饭 35」「打车去机场 120 公司报销」→ Agent 结构化（金额/类别/账户/标签/是否报销）→ 存账本 → 随时问「这个月吃饭花了多少」→ 月度报告（GenUI 图卡）。
- Agent 角色：自然语言→结构化记账（function calling 甜点场景）；分类与汇总是确定性。
- 底座关系：账本=新轻量实体；月报=定时基建+GenUI Chart；**录入摩擦接近零**是成败关键，恰好是本平台「统一输入框」哲学的延伸。
- 量级：M。不确定性：支付 App 自动导入不做（第三方集成边界）；手动记录的天花板要诚实——它服务「想记但嫌麻烦」的人，救不了「不想记」的人。

**L2. 发票/报销整理**
- 痛点：发票散落，报销如酷刑（M4）。
- 形态：发票图片/PDF 批量上传 → 多模态提取（抬头/税号/金额/日期/类目）→ 去重校验 → 按报销周期生成报销单 Artifact（表格+发票附件索引）→ 导出。
- Agent 角色：票据 OCR 与结构化；校验规则（连号、重复、抬头一致性）确定性。
- 底座关系：发票=image/document Artifact；报销单=report Artifact；与 L1 的「可报销」标签联动。
- 量级：M。不确定性：各地发票格式差异大，提取准确率需真实样本迭代；v1 允许人工校正（编辑器里改）。

**L3. 个人财务仪表盘**
- 痛点：财务黑盒（M5）。
- 形态：汇聚 L1 账本 + docs/7 D2 订阅审计 + 手动资产快照 → 月度仪表盘（支出结构/趋势/订阅占比/异常提醒）。
- Agent 角色：异常检测（环比突增提醒）；图表=确定性渲染。
- 底座关系：GenUI Chart 组件（与 docs/8 J1 年报共享数据可视化技能）；仪表盘=GenUI 页面；数据全来自平台内，无外部金融对接。
- 量级：S–M（L1 之后）。不确定性：价值完全依赖 L1 的数据积累，不可能先做。

### 簇 M · 个人自动化（对应 M6）

**M1. 自然语言自动化（个人 iPaaS 的最小核）**
- 痛点：人肉跨应用搬运（M6）。
- 形态：对输入框说「每周一早上把上周我创建的 Artifact 汇总发给我」「每天 18 点提醒我写日报」→ Agent 解析为**定时任务 + 动作模板** → 用户确认后生效 → 任务列表可管理。
- Agent 角色：自然语言 → cron + 动作（结构化解析，人确认）。
- 底座关系：这是 docs/7 A1「定时基建」的**泛化与产品化**——定时任务从「晨报专用」升级为「用户可编程」；动作白名单 v1 只含平台内动作（汇总/提醒/生成）。
- 量级：M。不确定性：外部动作（发邮件/发微信）=第三方集成边界，v1 不做；威力受限但边界清晰。

**M2. 网页变更监控**
- 痛点：盯某个页面（价格/职位发布/签证进度/图书馆新书）全靠人肉刷。
- 形态：登记 URL + 关注点（「价格低于 500 告诉我」）→ 定时抓取 → 语义 diff（不是文本 diff，是「用户关心的维度变了吗」）→ 命中提醒。
- Agent 角色：页面理解 + 条件判断。
- 底座关系：定时基建 + fetch_url Tool + 提醒卡片。
- 量级：M。不确定性：**反爬与合规是天花板**——只允许用户显式登记的少量页面、低频抓取（≥小时级），明确不做对抗（呼应 docs/7 反建议）。

**M3. 二手闲置出售助手**
- 痛点：闲置物品想出掉，估价、写文案、回复咨询都嫌烦。
- 形态：拍照 → 识别物品 → DeepResearch 查二手行情 → 生成发布文案（标题/描述/建议价）→ 售出后登记进 L1 账本（收入）。
- Agent 角色：多模态识别 + 行情研究 + 文案。
- 底座关系：DeepResearch 模板化复用 + L1 联动。
- 量级：S–M。不确定性：发布与沟通不接入平台外（只做「复制就绪」）。

**M4. 邮箱每日摘要（只读）**
- 痛点：重要邮件淹没在 newsletter 里。
- 形态：只读接入邮箱 → 每日摘要：需要回复的/纯通知的/可退订的 → 一键生成退订清单。
- Agent 角色：分类 + 摘要。
- 底座关系：**首次需要外部账户 OAuth**——这是 docs/7 反建议「不做邮箱客户端」的边界试探。
- 量级：L。不确定性：OAuth 与邮件数据敏感性是红线级问题；**建议列为「违反既定边界，除非用户强烈需求否则不做」**，放在这里是为了把边界讨论显式化。

## 3. 推荐 Shortlist（3 个 + 1 个架构议题）

1. **K2 截图管家（22 分）**：本轮最高分。截图是现代人的「外挂记忆」，几乎人人都有截图坟场。它把 C1 知识库从「文字」扩展到「图像」，多模态+OCR+语义检索三技能一次点亮。妥协点已明确：v1 手动上传，不做目录监控。
2. **L1 对话记账（21 分）**：「输入框即账本」与平台哲学完美同构，日常打开频率天花板高。与 L2/L3 形成财务小闭环，但后两者依附它存在，不单独立项。
3. **L2 发票报销（20 分）**：工作者季度级高痛场景，多模态提取+编辑器校正的组合是「AI 不完美也能用」的正确产品设计（人校正，不是 AI 全责）。
4. **K1 文件整理（18 分）——作为架构议题保留**：痛点最真、技能最新（受控本地执行），但它逼问一个根本问题：**平台要不要长出「本地伴侣进程」？** 这个问题值得单独写一份评估（形态、安全模型、更新机制），不应作为普通功能混入排期。

**M1 自然语言自动化（20 分）**不单列 shortlist 但强烈建议：它不是新功能，而是 docs/7 A1 定时基建的**必然进化**——定时基建做完时顺手把「用户可编程」开放出来，边际成本极低。

## 4. 与前两轮的协同

```text
K2 截图管家 ──吃── C1 知识库（embedding）──喂── 全平台（截图可被任何场景引用）
K3 文档结构化 ──喂── docs/7 D1 到期哨兵（合同到期日自动登记）
L1 记账 ──吃── docs/7 D2 订阅审计 ──喂── L3 仪表盘 + docs/8 J1 年报（年度花费）
M1 自动化 ──泛化── docs/7 A1 定时基建 ──承载── 一切「定期做 X」的历史候选
M3 闲置出售 ──复用── DeepResearch（行情）──喂── L1 账本（收入登记）
```

协同图再次出现枢纽：**C1 知识库与定时基建**。三轮脑暴累计 41 个候选，接近一半挂在这两个枢纽上——这是比任何单个候选都重要的结论。

## 5. 反建议（本轮）

| 方向 | 为什么不 |
| --- | --- |
| 邮箱/日历/支付账户的 OAuth 深度集成 | 边界外（docs/6 §11 已定）；M4 列为边界讨论样本而非候选 |
| 自动导入银行/支付流水 | 敏感金融数据 + 第三方集成双重红线；L1 坚持「手动但零摩擦」路线 |
| 文件自动删除/清理 | 整理=移动+可回滚，永不删除；删除权永远留给用户 |
| 投资跟踪与建议 | 金融建议红线（docs/7 已定）；L3 只做「记录与可视化」，不含任何建议 |
| 抢票/秒杀/高频监控 | 反爬对抗，docs/7 已定；M2 限低频少量页面 |
| 密码/密钥管理 | 安全责任不可承受；数字资产清单只记「有什么」，永不存凭据本身 |
