## 0. 摘要与结论速览

**总体结论：想法成立，且与现有架构高度兼容。** 现有平台最值钱的资产不是 Coding Agent 本身，而是它已经跑通的四样基础设施——**持久化 SSE 事件协议、Run 状态机（含 awaiting_approval 审批门）、Query/Zustand 前端状态分层、契约目录（contracts/）**。ChatBot 和 DeepResearch 都可以直接长在这四样资产上，不需要重造底座。

```text
                    │  首页：统一输入框 + 模式路由（§4）    │

              ┌─────────────────────┼──────────────────────┐
              ▼                     ▼                      ▼
      ┌──────────────┐     ┌────────────────┐     ┌────────────────┐

      └──────┬───────┘     └───────┬────────┘     └───────┬────────┘

             └───────────┬─────────┴──────────┬───────────┘
                         ▼                    ▼
              ┌────────────────────┐  ┌────────────────────┐
              │ 统一 Run/SSE 底座   │  │ 统一 Artifact 体系  │
              │（复用现有，扩展事件）│  │（新增：报告/网页/   │

              └────────────────────┘  └────────────────────┘
```

核心推荐立场（详见对应章节）：

| # | 决策点 | 推荐结论 |
| --- | --- | --- |
| 1 | 首页如何进入不同功能 | **混合式路由**：模式 Chip 显式选择为主 + 服务端轻量意图分类为辅 + 低置信度时用 GenUI 确认卡片反问（§4） |

| 7 | 实施节奏 | 四期推进，每期结束都可独立演示；现有 P1 缺口（Diff/恢复/访客）并行补，不被新功能饿死（§10） |

## 1. 背景与评估目标

### 1.1 用户想法复述

将当前「AI Coding 工作台」升级为综合性平台，承载三类能力积累：

1. **首页**：仍是入口 + 输入框，但需要一个清晰的机制进入不同功能；
2. **ChatBot**：服务端 Agent 调用模型/Tools/Search 回答问题，SSE 流式响应，答案支持 **Markdown 流**与 **DSL JSON Schema + 流式 data** 两种方式渲染——核心实验点是 SSE 协议 + GenUI 渲染引擎 + 问答 Agent + 多轮上下文管理；
3. **DeepResearch Agent**：多 Agent 实现，先生成研究计划 → 用户可修改并确认 → 研究过程可视化 → 产出研究报告 Artifact → 富文本编辑器展示，支持手动修改与选中内容 AI 二次精修；
4. **Coding Agent**：现有对话式代码构建能力，原样保留并归入平台。

同时希望方案不局限于上述功能，能覆盖 **GenUI、SSE、Agent、富文本/图片/视频/代码编辑器** 的技能实践，并结合日常应用场景。

### 1.2 评估准则

本文用四条准则衡量每个设计决定：

```text
准则一  技能成长价值 —— 这个功能/设计能否真实锻炼目标技能点？
准则二  架构一致性   —— 是否继承既有不变量（§2.2），不破例、不另起炉灶？
准则三  可实施性     —— 单人投入下能否分期落地、每期可演示？
准则四  日常价值     —— 除了练手，能否解决真实日常问题、值得长期使用？
```

凡两条以上准则不满足的方案，直接淘汰或降级为「后续再说」。

### 2.2 必须继承的架构不变量

以下不变量来自 AGENTS.md §3 与 docs/2、docs/3，**新功能一律不得破例**：

1. **事实来源三分**：Git = 源码与版本；Postgres = 产品状态与事件；Storage = 不可变 Artifact/日志/导出。新增「报告 Artifact」属于第三类，新增「会话/消息」属于第二类——各有归属，不搞 JSONB 大杂烩。
2. **SSE 走持久化 RunEvent**：事件带单调 sequence、Last-Event-ID 回放、410 快照恢复；禁止定时器伪造进度；事件只携带脱敏的产品级字段。
3. **密钥与凭据不出服务端**：浏览器只持有 Supabase Auth 身份；模型 Key、搜索 API Key、数据库凭据只在 Worker/服务端。
4. **Agent 是受限推理组件**：模型不直接持有平台权力。ChatBot 的 Search Tool、DeepResearch 的检索 Tool 同理——Tool 集合显式声明、入参出参受控、不暴露任意 Shell/任意网络。
5. **前端状态分层**：TanStack Query 管服务端事实，Zustand 管 UI 协调（连接状态、标签、布局），组件 state 管本地交互；新功能沿用，不在 Zustand 里复制消息/报告全文。
6. **契约版本化**：API/SSE/Artifact Schema 进 `contracts/`，生产者消费者一起改，兼容性显式声明。

### 2.3 可直接复用的资产清单

## 3. 产品定位升级：从「AI Coding 工作台」到「个人 AI 能力平台」

### 3.1 新定位

> **一个以「对话输入 → Agent 执行 → 产物沉淀」为主线的个人 AI 能力平台：同一个输入框背后，是可以问答（ChatBot）、可以研究（DeepResearch）、可以构建（Coding Agent）的三类 Agent；所有产出统一沉淀为可查看、可编辑、可回溯的 Artifact。**

这一定义的关键不是「三个功能拼盘」，而是**一条统一主线**：

```text
输入（首页统一输入框）
  → 路由（§4：显式 Chip / 意图分类 / @提及）
  → Run（统一执行单元：kind = chat | research，编码类沿用 initial/update/retry/restore）
  → 过程（统一 SSE：可解释、可恢复、可取消）
  → 产物（统一 Artifact：报告 / 网页 / 代码项目 / 图片 / 视频）
  → 沉淀（历史中心：按时间浏览所有 Run 与 Artifact）
```

### 3.2 信息架构

```text
/                      首页：统一输入框 + 模式 Chip + 最近会话/Artifact 速览
/chat/:conversationId  ChatBot 会话页（左：消息流；右：GenUI 画布/来源面板）
/research/:runId       DeepResearch 页（左：对话与计划；右：研究过程/报告）
/studio/:projectId     Coding Agent 工作台（现有 Workspace 页，URL 可保持 /projects/:id）
/artifacts             Artifact 中心（跨功能的产物列表：报告/网页/代码/图片/视频）
/history               运行历史中心（跨功能的 Run 列表：状态、耗时、产物入口）
/settings              模型/搜索 Provider、用量与预算
```

三个功能页共享同一套骨架：左栏对话/指令，右栏产物画布。这样「学一次交互，处处可用」，也让 GenUI 渲染引擎、Artifact 查看器成为跨功能复用的前端模块，而不是每个功能各写一套。

### 3.3 对现有用户的兼容性

- 现有项目工作台、URL、数据完全保留；Coding Agent 的页面可以作为 `/studio` 的别名存在，避免破坏性迁移。
- 首页从「项目列表 + 新项目输入」演进为「统一输入框 + 三模式 + 最近动态」；项目列表降级为「Coding 模式下的最近项目」区块，不丢失。

## 4. 首页与入口路由设计（问题 1）

### 4.1 三种候选方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A. 显式模式 Tab/Chip | 输入框上方固定三个模式按钮，用户先选再输入 | 确定性、零误判、实现最简单、对评审可解释 | 多一次点击；缺少「智能感」 | 作为**基础层**必须做 |
| B. 纯 LLM 意图识别 | 永远只有一个输入框，服务端分类后自动路由 | 最有「平台感」 | 误判成本=一次错误 Run；黑盒不可解释；分类本身消耗一次模型调用 | 单独使用不合格（准则二、三不达标） |
| C. 混合式 | 默认 auto：规则 + 轻量分类路由；用户可随时用 Chip 或 `@` 强制指定；低置信度时反问 | 确定性兜底 + 智能体验 + 误判可纠正 | 实现量略大 | **推荐** |

### 4.2 推荐方案：混合式路由（Auto + Chip + @提及 + 反问确认）

```text
┌──────────────────────────────────────────────────────────┐
│  [✨ Auto] [💬 问答] [🔬 深度研究] [🛠 构建应用]            │
│  ┌──────────────────────────────────────────────────┐    │
│  │ 输入任何问题、研究主题或应用想法…                    │    │
│  │ 支持 @chat / @research / @code 强制指定            │    │
│  └──────────────────────────────────────────────────┘    │
│  示例：「对比 2026 年主流向量数据库」 「帮我做个记账应用」  │
└──────────────────────────────────────────────────────────┘
                  │
                  ▼ 提交
        ┌──────────────────┐
        │ ① 显式信号优先     │  Chip 非 Auto？→ 直接路由
        │    @提及？         │  @research → DeepResearch …
        └───────┬──────────┘
                │ 无显式信号
                ▼
        ┌──────────────────┐
        │ ② 规则快速匹配     │  「帮我做个/生成一个应用/网站」→ code
        │   （零成本）       │  「调研/对比/深度分析…」→ research
        └───────┬──────────┘
                │ 规则未命中
                ▼
        ┌──────────────────┐
        │ ③ 轻量模型分类     │  小模型输出 {capability, confidence}
        │   （服务端，廉价） │  confidence ≥ 0.75 → 直接路由
        └───────┬──────────┘
                │ 置信度不足
                ▼
        ┌──────────────────────────────────────┐
        │ ④ GenUI 确认卡片反问（原地，不开 Run）   │
        │  「你想让我：」                          │
        │  [🔬 深度研究这个问题] [💬 直接回答]      │
        │  [🛠 构建一个相关应用]                    │
        └──────────────────────────────────────┘
```

设计要点：

1. **路由发生在服务端创建 Run 之前**。意图分类是 API 层的一次廉价调用（小模型、结构化输出、超时 2s），不进 Worker 队列；分类结果与置信度记入 Run 元数据，可审计、可复盘（这本身就是一个小型 Eval 数据集）。
2. **反问确认卡片用 GenUI 引擎渲染**（§5.4）。这是刻意的「狗粮」设计：平台第一个 GenUI 场景就是路由确认，用户第一天就能见到 GenUI 的价值，且场景简单、可控，适合作为 GenUI 引擎的首个验收用例。
3. **降级链完整**：分类模型超时/失败 → 落入默认 ChatBot 模式并在 UI 提示「已按问答处理，可重新指定」；规则匹配永远是零成本兜底。
4. **模式可切换**：进入某功能后，顶部保留模式标识；用户发现走错时，输入框仍然支持 `@` 重新指定，原上下文摘要随指令携带（例如从 ChatBot 转 DeepResearch 时带上当前问题）。
5. **分期落地**：第 1 期先上「Chip + @提及 + 规则匹配」，规则未命中一律落入 ChatBot 并提示可重新指定（零模型成本，先跑通主链路）；第 2 期再补「轻量模型分类 + GenUI 反问卡片」。这样路由不阻塞 ChatBot 基座开发，GenUI 引擎就绪前也不欠体验债。

### 4.3 首页其余构成

```text
┌──────────────────────────────────────────────┐
│ 统一输入框（§4.2）                              │
├──────────────────────────────────────────────┤
│ 继续上次：                                      │
│  🔬 「向量数据库对比」研究 · 报告已完成  2h 前    │
│  💬 「React 19 新特性」问答 · 12 条消息  昨天     │

├──────────────────────────────────────────────┤
│ 最近产物：                                      │
```

## 5. 功能一：ChatBot（SSE + GenUI 实验场）

### 5.1 功能定义与技能映射

| 产品能力 | 对应技能实验点 |
| --- | --- |
| 流式问答（Markdown） | SSE 协议：连接、增量帧、断线续传、取消 |
| 工具调用（Search 等） | Agent Tool 设计、工具结果的结构化呈现 |
| GenUI 结构化回答 | DSL Schema 设计、流式 JSON、渲染引擎、降级 |
| 多轮对话 | 上下文窗口管理、摘要压缩、引用上一轮产物 |

### 5.2 架构

```text
浏览器                              服务端
┌─────────────────┐  POST /chat/conversations/:id/messages
│ ChatPage         │ ──────────► API：鉴权 + 建 chat Run（幂等）
│ ┌─────────────┐ │                     │
│ │ 消息流       │ │                     ▼
│ │ (Markdown /  │ │            Worker 领取 chat Run
│ │  GenUI 渲染) │ │                     │
│ └─────────────┘ │            Chat Agent（Deep Agents 入口）
│ ┌─────────────┐ │            ├─ 模型流式输出
│ │ 来源/工具面板 │ │            ├─ Tools：web_search / datetime /
│ └─────────────┘ │            │      calculator（显式白名单）
└────────┬────────┘            └────────┬───────────┘
         │  GET .../events (SSE)        │ 事件写入
         │  Authorization: Bearer       ▼
         └───────────────── run_events（产品级事件）
                           + 瞬态 delta 帧（不持久化，§5.3）
```

### 5.3 流式协议：两类帧，一个连接（关键设计）

现有 `run_events` 是**产品级事件**（持久化、带 sequence、可回放）。ChatBot 的 token 增量如果逐 token 持久化，一次回答会产生数百行事件，污染回放语义、撑爆表体积。因此建议在同一 SSE 连接上区分两类帧：

```text
SSE 连接 GET /v1/chat/runs/:runId/events
│
├─ 持久化事件（进 run_events，带 id/sequence，可回放）
│   chat.run.started        { conversationId, messageId }
│   chat.tool.started       { tool: "web_search", query }
│   chat.tool.completed     { tool, resultRef }        ← 大结果存 Storage
│   chat.message.completed  { messageId, format, charCount }
│   chat.run.failed / cancelled
│
└─ 瞬态帧（不持久化、不带 sequence、不可回放）
    event: chat.delta
    data: {"messageId":"m_01","kind":"markdown","text":"React 19 的"}
    event: chat.delta
    data: {"messageId":"m_01","kind":"markdown","text":"新特性包括…"}
    event: chat.ui.block
    data: {"messageId":"m_01","index":3,"node":{...GenUI 节点…}}
```

连接引导与取消语义：

- 前端 `POST /chat/conversations/:id/messages` 的响应携带 `runId + messageId + 当前最大 sequence`，随后用这些参数建立 SSE——避免「先连流再等 runId」的竞态；
- 生成中取消沿用协作式取消：`POST /runs/:id/cancel` → Worker 停模型流 → 已生成部分**保留**为消息（`status: cancelled`，已落库的持久化事件不变），前端把半截消息标为「已停止」，不回滚、不假装没发生。

恢复语义：断线重连后，客户端从 `chat.message.completed` 之前的最后一个持久化事件 + 消息快照重建；**正在生成中的瞬态 delta 不重放**——重连后若消息未完成，服务端从断点继续推 delta（Worker 侧的模型流未中断时），否则以已持久化的部分文本为起点。这与 Coding Agent「事件可完整回放」的承诺不同，需要在契约里显式写明：**chat 的可回放单位是消息，不是 token**。

> 该设计是对不变量 2 的「细化」而非「破例」：持久化事件仍承载全部产品级事实（哪条消息、用了什么工具、成功失败）；瞬态帧只是同一连接上的显示优化，不含任何不可再生的信息。

### 5.4 GenUI 渲染引擎（核心实验点）

**DSL 设计原则：白名单组件 + 扁平 block 流 + 前后端双重校验。**

```text
GenUI 文档 = 有序 block 列表（v1 只追加，不修改）
每个 block = { id, component, props, children? }

v1 组件白名单（约 10 个，宁少勿多）：
  Text / Heading / List / Table / KeyValue
  Card / Callout / Image / Divider / ActionButtons / SearchResults

示例（一个回答 = markdown 段 + GenUI 段混排）：
  block[0] { component:"Text", props:{ markdown:"查到了 3 个方案：" } }
  block[1] { component:"Table", props:{ columns:[...], rows:[...] } }
  block[2] { component:"ActionButtons", props:{ actions:[
               { label:"深入研究这个话题", intent:"@research <当前问题>" },
               { label:"做成对比页面",     intent:"@code 生成对比页" } ] } }
```

渲染与降级管线：

```text
模型输出（服务端约束为 JSON 协议）
  → Worker 逐 block 校验（contracts/genui/v1.schema.json）
  → 校验通过：chat.ui.block 帧推送
  → 校验失败：该 block 自动转为等价 Markdown 文本帧，并记 build 级诊断
        │
        ▼
前端渲染引擎（features/genui/）
  ├─ registry.ts        组件名 → React 组件映射（未知名 → 降级渲染）
  ├─ renderer.tsx       block 树 → React 树（流式 append，已渲染 block 不重绘）
  └─ fallback.tsx       任何异常 → Markdown 渲染该段，UI 角标提示「已降级」
```

要点：

- **ActionButtons 是 GenUI 的灵魂**：按钮 intent 直接回流到统一输入框路由（§4.2），形成「回答 → 建议下一步 → 一键发起研究/构建」的闭环。这让 GenUI 不只是展示，而是**可操作界面**——也是和纯 Markdown 回答拉开体验差距的地方。
- 流式体验上，GenUI block 与 Markdown delta 可以交错：叙事部分流式打字，结构化部分整块出现。v1 不做「半个 Table 逐行流入」的细粒度流式 JSON（部分 JSON 解析复杂度高、收益低），列为 v2 实验项（可用流式 JSON Patch / incremental parse 练手）。
- Search 工具结果渲染为 `SearchResults` block：标题、摘要、来源链接、引用编号——为 DeepResearch 的引用体系（§6.4）提前练兵。

### 5.5 多轮上下文管理

```text
每轮请求注入：
  system prompt（角色 + 输出协议：何时 markdown、何时 GenUI）
  + conversation summary（超过 N 轮后由后台任务滚动压缩）
  + 最近 K 轮完整消息（K≈8，按 token 预算截断）
  + 显式引用（用户 @ 引用的历史消息/Artifact 摘要）

持久化：
  chat_messages：role / content / content_format(markdown|genui) /
                 genui_doc（最终校验通过的 block 文档）/ summary / token_count
  滚动摘要写回 conversations.summary，压缩动作本身是后台 Run（可观测）
```

与现有 `messages` 表模式一致：只存用户可见内容与脱敏摘要，不存原始 Tool 轨迹（不变量：事件与消息不泄露内部细节）。

### 5.6 验收要点

- 断网 5 秒重连：消息继续或从快照恢复，不重复渲染、不丢已完成消息；
- 生成中取消：半截消息保留并标记「已停止」，持久化事件不受影响；
- 多轮对话超过摘要阈值后，仍能正确引用早期轮次的关键结论（摘要压缩不失真）；
- GenUI 渲染故意注入非法组件/非法 props：服务端拒收并降级，前端不白屏；
- ActionButton 点击正确回流路由（`@research` → 创建研究计划）；
- 工具调用全程可见（tool.started/completed），结果链接可点开。

## 6. 功能二：DeepResearch Agent（多 Agent + Artifact 编辑器实验场）

### 6.1 功能定义与技能映射

| 产品能力 | 对应技能实验点 |
| --- | --- |
| 研究计划生成与确认 | 结构化输出 + 人机协作审批门（复用 awaiting_approval） |
| 多 Agent 并行研究 | LangGraph 编排、子任务隔离与汇总、成本控制 |
| 思考过程展示 | SSE 事件契约设计、过程可视化 UX |
| 报告 Artifact | 长文生成、分节流式、来源引用、版本化 |
| 富文本编辑 + 选区 AI 精修 | TipTap 编辑器、选区协议、流式改写、编辑历史 |

### 6.2 多 Agent 编排

```text
用户问题
   │
   ▼
┌────────────┐   计划（研究目标/子问题/章节大纲/检索策略/预算）
│  Planner    │ ──────────────────────────────────────┐
└────────────┘                                       ▼
                                        ┌────────────────────┐
                                        │ 计划卡片（可编辑）    │  ← 复用 PlanCard 模式
                                        │ [修改] [确认并开始]   │
                                        └─────────┬──────────┘
                                                  │ 确认（复用 awaiting_approval 语义）
                                                  ▼
                              ┌───────────────────────────────────┐
                              │ Orchestrator（Worker / LangGraph） │
                              └───────┬───────────┬───────────┬───┘
                                      ▼           ▼           ▼
                                ┌──────────┐┌──────────┐┌──────────┐
                                │Researcher││Researcher││Researcher│ 每个子问题一个子 Agent：
                                │ 子问题 1  ││ 子问题 2  ││ 子问题 3  │ 独立上下文 + Search/读取 Tool
                                └────┬─────┘└────┬─────┘└────┬─────┘
                                     └───────────┼───────────┘
                                                 ▼ 子结论 + 来源（带引用编号）
                                        ┌────────────────┐
                                        │  Synthesizer    │ 交叉验证、去重、冲突标注
                                        └───────┬────────┘
                                                ▼
                                        ┌────────────────┐
                                        │  Writer         │ 按章节流式写入报告 Artifact
                                        └───────┬────────┘
                                                ▼
                                        报告 Artifact（markdown 源 + 渲染视图 + 引用列表）
```

边界规则（与现有「Agent 是受限推理组件」一致）：

- Planner/Researcher/Synthesizer/Writer 都只有声明式 Tool（`web_search`、`fetch_url`、`emit_note`），**不**持有数据库、Shell、任意网络（`fetch_url` 抓取指定 URL 正文，带域名/大小/超时限制；命名刻意区别于 Coding Agent 读 worktree 源码的 `read_source`，两者权限域不同）；
- 子任务数量上限（默认 ≤ 5）、每子任务来源上限、整 Run token/时长预算，超限优雅降级为「部分完成 + 明确标注缺口」；
- Orchestrator 是确定性代码：决定并行度、收集子结论、写事件、推进状态机——Agent 不自我编排。

### 6.3 状态机：与现有 Run 同一语言

```text
research Run:
queued → claimed → running(planning) → awaiting_approval
        →（确认计划，同一 Run 重新入队）→ running(researching)
        → running(synthesizing) → running(writing) → completed
                          ↘ cancelling → cancelled / ↘ failed

Run stage: planning → researching → synthesizing → writing
（与 Coding Agent 的 planning → generating → … → promoting 平行）
```

「确认计划」完全复用 `awaiting_approval`：释放 Worker 租约、前端展示可编辑计划卡片、批准后同一 Run 重新入队。计划本身像 Contract 一样**版本化**（每次编辑产生新版本，批准后冻结为该 Run 的输入快照）。

### 6.4 思考过程与来源引用的事件契约

新增 `research.*` 事件命名空间（进 `contracts/sse/`，schemaVersion 升级或并行 v2 命名空间，见 §9.3）：

```text
research.plan.ready        { planVersion, outline, subQuestions, budget }
research.subtask.started   { subtaskId, question }
research.thought           { subtaskId, kind: reasoning|search|reading, text }
research.source.found      { subtaskId, sourceId, title, url, snippet }
research.subtask.completed { subtaskId, conclusionRef, sourceIds }
research.section.started   { sectionId, title }
research.section.delta     （瞬态帧：报告分节流式）
research.completed         { artifactId, sectionCount, sourceCount }
```

「思考过程」的展示边界要想清楚：`research.thought` 展示的是**面向用户的脱敏摘要**（「正在检索 X」「已排除低可信来源 Y」），不是模型的原始推理链——与现有 SSE 脱敏不变量一致。引用体系贯穿全程：报告正文的 `[1][2]` 脚注 ↔ 来源面板 ↔ 点击打开原链接，引用编号由 Orchestrator 统一分配，避免 Writer 幻觉出不存在的来源。

### 6.5 报告 Artifact 与富文本编辑器

技术选型建议：**TipTap 2**（React 生态成熟、schema 可定制、选区 API 完备、可序列化为 Markdown/JSON）。当前前端无富文本依赖，属于新增依赖，需在实施时锁定版本。

```text
报告页布局：
┌────────────────────┬───────────────────────────────────┐
│ 左：对话与过程        │ 右：报告画布                         │
│  研究问题…           │ ┌───────────────────────────────┐ │
│  计划（已确认 v2）    │ │ TipTap 编辑器                   │ │
│  过程时间线（可折叠）  │ │  - 分节标题 / 正文 / 表格        │ │
│  来源面板 [1]-[12]   │ │  - [1] 引用脚注 → 点击定位来源    │ │
│                    │ │  - 选中文本 → 浮动 AI 菜单：      │ │
│                    │ │    [精修] [扩写] [简化] [翻译] […] │ │
│                    │ └───────────────────────────────┘ │
│                    │ 版本：v3（AI 精修） ▾  [导出 Markdown/PDF] │
└────────────────────┴───────────────────────────────────┘
```

选区 AI 精修协议：

```text
前端：selection（文档内锚点范围）+ instruction
  → POST /artifacts/:id/refine  { selectionAnchor, instruction, artifactVersion }
服务端：
  → 校验归属与版本 → 解析选区原文 → 构建精修 prompt（原文 + 指令 + 上下文窗口）
  → 创建短命 refine Run（复用 agent_runs / run_events，与 chat 同一 SSE 端点）
  → 流式改写（SSE 瞬态 delta，前端在选区内流式替换预览）
  → 用户 [接受] → 落库为新 artifact_version（标记 origin: ai-refine）
       [拒绝] → 丢弃，版本不变
```

关键设计：

- **每次 AI 精修产生一个 Artifact 版本**，接受/拒绝显式化——把 Coding Agent「失败不动稳定版本」的思想搬到编辑器里，撤销 = 回退版本，不依赖编辑器自身的 undo 栈跨会话恢复。
- 手动编辑与 AI 精修同源版本化：`artifact_versions(origin: generate|manual|ai-refine, …)`，版本列表可回溯对比（轻量 diff，复用未来 Coding Agent 的 Diff 视图组件）。
- 报告源格式为 Markdown，**按版本存 Storage（不可变 Artifact，与 §9.1 归属一致；本地卷 → Supabase Storage 随 P1 适配切换）**，DB 只存 ref 与 hash；TipTap 只负责编辑视图与 JSON ↔ Markdown 序列化转换。导出 Markdown 因此是零成本（直接取 Storage 对象），PDF 导出列为可选。
- 图片/视频：研究过程中检索到的关键图可作为报告插图（链接引用 + 本地下载存 Storage 两档）；视频暂不嵌入报告，但进入统一 Artifact 体系（§8.1）。

### 6.6 验收要点

- 计划可编辑、可确认、确认后同一 Run 继续（不出现第二个 Run）；
- 三个子任务并行时事件不交错错乱（subtaskId 隔离）、取消后子任务全部终止；
- 报告中每个引用编号都能对应到来源面板的真实 URL；
- 选区精修流式可见、可接受/拒绝；接受后版本 +1 且可回退；
- 超预算时报告标注「未完成章节」，不静默截断。

## 7. 功能三：Coding Agent 的归位

**原则：一行不改其内核。** 现有「计划 → 审批 → 生成 → 校验 → 构建 → 提交 → 预览」闭环是平台可信度最高的资产，本次升级只做三件事：

1. **接入统一入口**：首页 `@code`/「构建应用」Chip → 创建项目并跳转现有工作台；工作台 URL 与数据不变。
2. **接入统一历史**：Coding 的 Run 进入跨功能历史中心（§8.3）；项目列表从首页降级为「构建应用」模式的最近项目区块。
3. **产物口径统一**：每个项目的稳定预览登记为 `type=web` 的 Artifact（只登记元数据与预览票据入口，不动 Git/构建链路），让 Artifact 中心能列出「我构建的网页」。

现有 P1 缺口（Diff/恢复 UI、导出、访客模式、Storage 适配）**不在本次升级范围内自动消失**，§10 会把它们排进并行轨道，避免「新功能热闹、老欠账不还」。

## 8. 增量建议（超出原始想法的部分）

以下建议按「技能成长价值 × 日常价值」筛选，均不破坏既定边界。

### 8.1 统一 Artifact 体系与类型化编辑器/查看器（强烈建议）

把「产物」提升为跨功能一等实体——这是把三个功能从「拼盘」变成「平台」的关键，同时一次性覆盖你想练的全部编辑器技能：

```text
artifacts 表（概念模型，详见 §9）
  id / ownerId / type / title / sourceRef( run | conversation | project )
  currentVersionId / createdAt / updatedAt

type → 打开方式（查看器/编辑器注册表，前端 features/artifacts/registry）
  report  → TipTap 富文本编辑器（§6.5）          → 练：富文本
  web     → 预览票据 + iframe（复用 Preview Gateway）→ 练：隔离预览
  code    → CodeEditor（现有）→ 可升级 Monaco      → 练：代码编辑器
  image   → ImageViewer（现有，可扩展标注）        → 练：图片查看/编辑
  video   → HTML5 播放器 + 关键帧/截帧（后续）     → 练：视频处理
  data    → 表格/图表查看器（GenUI Table 复用）     → 练：数据可视化
```

要点：

- **Artifact 与产生它的能力解耦**：报告来自 DeepResearch、网页来自 Coding Agent、图片可以来自 ChatBot 的图像工具或用户上传。Artifact 中心因此成为「我的 AI 资产库」。
- 查看器注册表与 GenUI 的组件注册表是**同一种模式**（白名单 + registry + fallback），做一次、练两遍。
- 图片/视频不必一步到位：v1 只做「查看 + 元数据」，标注、截帧、裁剪作为后续练手项，避免拖慢主线。

### 8.2 日常场景组合用例（平台真正的黏性来源）

单功能 Demo 打动评审，场景串联才能打动日常的自己。建议围绕 4 个真实场景验收平台：

| 场景 | 链路 | 练到什么 |
| --- | --- | --- |
| 旅行规划 | ChatBot 问答 → GenUI 行程卡片 → 「深入研究目的地」→ DeepResearch 报告 → 编辑器精修为出行清单 | GenUI 表单/卡片、跨功能跳转、报告编辑 |
| 行业/技术周报 | DeepResearch 定时发起（预设 prompt）→ 报告 Artifact → 选区精修 → 导出 Markdown 发飞书/邮件 | 预设与复用、引用体系、导出 |
| 学习笔记 | ChatBot 学新概念 → 代码块/表格回答 → 「存为 Artifact」→ Artifact 中心按主题回顾 | 上下文管理、Artifact 沉淀 |
| 小工具自救 | 「帮我做个 XX 页面」→ Coding Agent → 预览 → 迭代 → 导出 ZIP | 现有闭环的日常化 |

### 8.3 低成本高价值的配套项

- **Prompt/预设库**：保存常用指令（研究模板、周报模板），首页一键发起；实现成本极低，日常使用频率最高。

- **Eval 面板**：把现有三个标准 Eval 场景 + 新增的 chat/research 场景做成固定用例集，每次大改后跑一遍；对个人项目，这是「面试时能讲质量故事」的直接证据。

## 9. 数据模型与契约扩展

### 9.1 新增实体（概念模型，最终以 migration 为准）

```text
                        现有                                 新增
┌──────────────────────────────┐   ┌───────────────────────────────────┐
│ projects                     │   │ conversations                      │
│ agent_runs ──────────────┐   │   │  id/owner_id/title/summary/…       │
│  kind: initial|update|…   │   │   │ chat_messages                      │
│  + 新 kind: chat|research │◄──┼───┤  conversation_id/run_id/role/      │
│ run_events ──────────────┘   │   │  content/content_format/genui_doc/ │
│  + chat.* / research.* 事件   │   │  summary/token_count               │
│ build_contracts（编码计划）   │   │ research_plans（研究计划，版本化）    │
└──────────────────────────────┘   │ artifacts                          │
                                   │  id/owner_id/type/title/source_ref/│
                                   │  current_version_id                │
                                   │ artifact_versions                  │
                                   │  artifact_id/version/origin:       │
                                   │  generate|manual|ai-refine/        │
                                   │  storage_ref/parent_version_id     │
                                   │ sources（研究来源，供引用编号）       │
                                   └───────────────────────────────────┘
```

归属判定（沿用事实来源三分原则）：

- 会话、消息、研究计划、Artifact 元数据 → **Postgres**（产品状态）；
- 报告全文、GenUI 文档快照、大图/大文件 → **Storage**，DB 只存 ref 与 hash；
- 代码项目源码 → **Git**（不变）。

### 9.2 与 agent_runs 的关系

建议**复用** `agent_runs` 而非新建并行表：`kind` 扩展 `chat | research`，新增可空的 `conversation_id` / `artifact_id` 关联列；队列、租约、幂等键（request_id）、取消、事件写入全部免费继承。这与 docs/3「agent_runs = 用户动作 + 队列任务的唯一模型」的结论一致——若新建 `chat_jobs` 之类并行队列表，等于重犯当初否决 `agent_jobs` 的错误。

### 9.3 SSE 契约扩展方式

- 信封不变（`schemaVersion/runId/sequence/at/payload`）；
- 事件类型按命名空间增量扩展：`chat.*`、`research.*`、`artifact.*`，全部登记进 `contracts/sse/`（新增 `chat.v1`、`research.v1` 分 schema 或 v1.schema.json 增补枚举——实施时二选一，倾向分文件，便于按能力独立演进）；
- **瞬态帧（chat.delta / chat.ui.block / research.section.delta）单独一节定义**：不持久化、不参与 Last-Event-ID 回放、不带 sequence，契约中显式标注「ephemeral」；
- 前端 SseTransport 适配层同步扩展：无 `id` 的 ephemeral 帧直接透传给消息渲染旁路，**不更新** `lastEventId`、不参与 sequence 去重/缺口检测——持久化事件的既有规则（重复忽略、缺号取快照）原样保留；
- 前后端类型从 schema 生成，新增事件类型必须同步更新消费端 reducer，未知事件类型前端忽略但不报错（向前兼容）。

### 9.4 前端模块落位（延续 docs/4 规则）

```text
features/
  chat/        # 会话页、消息流、Markdown 渲染、工具面板
  genui/       # GenUI registry/renderer/fallback（被 chat、首页确认卡片复用）
  research/    # 计划卡片（从 contracts 的 PlanCard 抽通用模式）、过程时间线、来源面板
  artifacts/   # Artifact 中心、查看器注册表、TipTap 报告编辑器、版本列表
  runs/        # 现有：扩展为跨 kind 的 Run 投影与历史中心
  workspace/   # 现有 Coding 工作台，不动物理结构
shared/markdown/  # 统一 Markdown 渲染（GFM + 代码高亮 + XSS sanitize）
```

新增依赖预估：`react-markdown`（或 unified 系）、`@tiptap/*`、（可选）`monaco-editor`。均需在实施期锁定版本并过一遍包体积检查；**禁止**为了省事引入整套低代码/富文本平台级依赖。

## 10. 实施路线与优先级

### 10.1 分期（每期结束都可独立演示；单人节奏预估，弹性 ±50%）

```text
第 1 期（约 2 周）ChatBot 基座
  范围：conversations/chat_messages 表、chat Run、Markdown delta 流（瞬态帧）、
        web_search Tool、断线重连/取消、首页路由 v1（Chip + @提及 + 规则匹配，
        未命中默认进 ChatBot 并提示可重新指定）
  验收：一轮带搜索的多轮对话，断网 5s 重连不丢消息；取消后半截消息正确标记；
        37 项旧测试 + 新增测试全绿
  不验收：GenUI、意图分类模型（下一期）

第 2 期（约 2 周）GenUI 引擎 + 路由 v2
  范围：genui v1 schema（~10 组件）、服务端逐 block 校验、前端 registry/renderer/
        fallback、ActionButtons 回流路由、轻量意图分类上线、
        低置信度反问卡片（用本期 GenUI 引擎渲染，作为引擎首个真实用例）
  验收：注入非法组件自动降级 Markdown 不白屏；确认卡片可正确路由三类意图
  风险点：DSL 范围蔓延 → 组件超 10 个一律进 backlog

第 3 期（约 3–4 周）DeepResearch + 报告编辑器
  范围：research Run 状态机（复用 awaiting_approval）、Planner/Orchestrator/
        Researcher xN/Synthesizer/Writer、research.* 事件、来源面板、
        artifacts + artifact_versions、TipTap 编辑器 + 选区精修 + 版本回退
  验收：§6.6 全部要点；一次完整研究可演示（问题→计划→确认→过程→报告→精修）

第 4 期（约 1–2 周）整合打磨
  范围：首页「继续上次/最近产物」、跨功能历史中心、Prompt 预设库、
        Artifact 中心（web/code/image 查看器接线）、Eval 面板雏形
  验收：§8.2 四个日常场景至少两个完整走通并录屏存档

并行轨道（不阻塞主线，每周固定 20% 时间）
  现有 P1 缺口：Diff/恢复 UI → 访客模式 → 导出 ZIP → Storage 适配
  理由：老欠账不清，平台永远在「半成品」状态，评审时第一个被问的就是它
```

### 10.2 排序逻辑

1. **ChatBot 先于 DeepResearch**：SSE 瞬态帧、Tool 设计、SearchResults 组件都是 DeepResearch 的积木，先在简单场景踩坑；
2. **GenUI 独立成期**：它是全新前端引擎，混在任何功能里做都会失控；且首页确认卡片给它一个天然首用例；
3. **DeepResearch 最重放第三**：前两期的协议、组件、审批门全部就位后，它主要是编排与编辑器工作；
4. **整合放最后**：历史中心、Artifact 中心依赖前三期的产物真实存在才有意义。

### 10.3 质量门槛（沿用 AGENTS.md §6，新增条目）

- 每个新事件类型：schema 校验测试 + reducer 测试（重复/缺号/未知类型）；
- GenUI：服务端拒收非法 DSL 的负路径测试 + 前端降级快照测试；
- DeepResearch：多子任务并行事件隔离测试、预算超限降级测试、精修接受/拒绝版本测试；
- 编辑器：选区锚点在文档编辑后的定位稳定性测试；
- 每期结束：旧 37 项测试 + 全部新增测试绿，`pnpm build/lint`、`ruff`、`tsc` 通过。

## 11. 风险与取舍

| 风险 | 等级 | 应对 |
| --- | --- | --- |
| 范围爆炸：三功能 + Artifact + 编辑器同时铺 | 高 | 严格分期（§10），每期有可演示验收；任何「顺便做」进 backlog；并行轨道锁死 20% 时间 |
| GenUI DSL 设计成无底洞 | 中 | v1 白名单 ≤ 10 组件、只追加不 patch；细粒度流式 JSON 留 v2；写 schema 前先写 5 个真实用例反推 |
| DeepResearch 成本/时长失控 | 中 | 子任务/来源/token/时长四重预算；超限降级为「部分完成 + 标注缺口」；预算参数进 Run 元数据可审计 |
| 瞬态 delta 与持久化事件语义混淆 | 中 | 契约单节定义 ephemeral 帧；reducer 测试覆盖「重连后不重复渲染」；文档写明可回放单位=消息 |
| 思考过程泄露原始推理/敏感信息 | 中 | `research.thought` 只发面向用户的脱敏摘要；沿用 SSE 脱敏审查 |
| 富文本 XSS | 中 | TipTap 输入输出 sanitize；Markdown 渲染统一走 shared/markdown（禁 raw HTML 或白名单 sanitize） |
| 报告引用幻觉（编造来源） | 中 | 引用编号由 Orchestrator 统一分配，Writer 只能引用已登记 sourceId；落库前校验每个编号 |
| 老 P1 缺口被无限期搁置 | 中 | 并行轨道写进节奏，每周固定时间；评审叙事上把「补缺口」也当成绩 |
| 搜索 Provider 依赖（Key 配额、结果质量、合规） | 低 | Provider 可配置（settings 页）；搜索 Key 只存服务端；结果缓存 + 每 Run 搜索次数上限控制配额 |
| 新增前端依赖失控（包体积/维护） | 低 | 锁定版本、评估包体积；monaco 等重依赖只在确实需要时引入 |

**明确的取舍（写下来防止反复）：**

- 不做多人协作、不做公开分享链接（沿用现有决定）；
- 不做通用插件市场/任意 MCP 接入——Tool 白名单手工维护；
- v1 不做视频生成，视频仅作为 Artifact 查看对象；
- 意图分类只用小模型，不为路由训练/微调任何模型；
- Artifact 中心 v1 不做全文搜索，只做列表 + 类型筛选。
